# 发布并触发构建

仅编排发布说明、分支合并、标签与推送。复用仓库已有的标签驱动 CI；不实现打包逻辑，不创建托管平台 Release，不等待或监控构建。

## 遵守发布契约

- 始终按“用户明确值 → 仓库证据 → 询问用户”的优先级确定每个值。不要用个人经验填补项目名、远端、分支、发布说明路径、标签格式、标签类型、构建平台或产物。
- 把发布契约视为一个整体：项目名、版本、精确标签、标签类型、源分支、发布分支、远端、上一个发布基线、最终发布内容的提交范围、发布说明路径与格式、提交信息、CI 验证状态和执行模式。能验证 CI 时记录精确标签过滤条件与已知产物；用户明确允许未验证触发时，未知产物信息可以保持未知。
- 当证据冲突、缺失或存在多个合理候选时，只询问缺失或冲突项；在契约完整前保持只读。
- 只有仓库中的 CI 配置能证明精确标签匹配触发条件时，才把触发条件标为“已验证”。无法证明时必须先询问；用户明确要求继续后可执行，但全程标为“触发条件未验证”。若配置证明标签不匹配，停止并要求修正契约。

## 只读预检

1. 记录开始时的分支与提交。第一项检查必须是 `git status --porcelain`。只要有任何输出（包括未跟踪文件），立即停止；列出状态，不切换分支、不抓取远端、不创建或修改文件，也不提交、合并、打标签或推送。
2. 用只读命令确认当前分支、HEAD、上游、ahead/behind 状态、所有远端和远端符号 HEAD。优先采用源分支上游所对应的远端；没有唯一证据时询问，不自动挑选。
3. 检查本地及远端分支与标签、最近标签的命名和对象类型、标签所在分支、已有发布说明、变更日志、历史发布提交和项目清单。通过 `git ls-remote` 获取远端事实，预检期间不要用 `fetch` 改变引用。
4. 检查仓库内全部 CI 配置和发布文档，定位精确的标签过滤条件、工作流入口、构建矩阵、产物名称与产物去向。区分“推送标签会请求运行”与“构建已经成功”。
5. 计算上一个适用标签之后、预期最终发布内容会包含的提交集合：同时检查源分支和发布分支，去重纳入发布分支独有提交；首次发布则分析两条分支的完整可达历史并明确标注。无法可靠确定最终范围时停止。若范围没有可发布的新提交，停止且不产生发布；除非用户在看到事实后明确要求空发布。
6. 确认目标标签在本地和所选远端都不存在。即使同名标签指向预期提交，也不得覆盖或复用。
7. 确认源分支不是 detached HEAD，且不会因远端领先而产生非快进推送。确认远端发布分支存在；若需要创建远端分支，必须由用户明确授权。

## 预览并确认

在任何写操作前展示一份中文预览，至少包含：

- 项目名、版本、精确标签及标签类型；
- 上一个发布基线与提交范围；
- 发布说明文件、源分支、发布分支和远端；
- CI 配置证据、标签匹配结果和已知产物；
- 正常发布或 `no-push` 模式，以及将发生的提交、切换、合并、标签和推送。

明确请求用户确认该预览。未确认时停止。确认后重新检查工作区与关键引用；若相较预览发生变化，停止并重新预检。

## 生成独立发布说明提交

1. 必要时切换到已确认的源分支，并再次确认当前分支正确、工作区干净、HEAD 与预览一致且源分支未落后于其远端分支；无法安全切换或引用发生变化时停止。
2. 遵循现有发布说明的位置、命名、语言和结构；若仓库没有可证明的约定，先询问用户，不新造路径或格式。
3. 仅依据已确认的最终发布提交范围撰写事实性摘要。沿用仓库惯例组织功能、修复、兼容性、升级提示和已验证的产物信息；不要声称产物已经生成。
4. 只暂存发布说明文件，检查 staged diff 中没有其他文件，然后单独提交。提交信息沿用已确认的仓库发布提交惯例；没有可证明的惯例时先询问用户，不自行发明格式。
5. 记录发布说明提交的 OID。任何生成、暂存或提交失败都立即停止，不继续合并或打标签。

## 执行正常发布

严格按以下顺序执行，不并行推送：

1. 将源分支的精确引用推送到已确认远端。失败时停止；不得切换发布分支、创建标签或声称已触发 CI。
2. 获取远端发布分支的最新引用并切换到本地发布分支。本地分支不存在时，从该远端引用建立跟踪分支；本地分支落后时只允许快进。本地分支领先或分叉时停止，禁止 reset、rebase 或覆盖。
3. 若源分支与发布分支不同，将源分支合入发布分支。采用仓库明确规定的合并策略；没有规定时执行普通非交互合并，不 squash、不 rebase。发生冲突时立即执行 `git merge --abort`，确认工作区恢复后返回原分支并停止；不得创建标签。
4. 将发布分支的精确引用推送到已确认远端。失败时停止且不得创建标签。推送成功后，用远端查询确认发布分支指向本地最终 HEAD。
5. 在发布分支最终 HEAD 上按已确认类型创建精确标签。创建前再次确认本地和远端均无同名标签，并验证标签解析到该 HEAD。
6. 只推送该精确标签。命令失败时保留本地标签，查询并报告远端实际状态，但不得声称 CI 已触发，也不得自动删标签或重写历史。
7. 标签推送命令成功后，确认远端标签（含 annotated 标签的 peeled commit）解析到发布分支最终 HEAD。随后返回开始时的原分支。

当源分支就是发布分支时，跳过切换和合并；源分支推送同时满足发布分支推送，但仍须在确认远端分支 OID 后才能创建标签。

## 执行 `no-push` 本地准备

- 允许获取远端引用，但禁止任何 branch push 或 tag push；不要把隐式默认 push 当作例外。
- 创建独立发布说明提交后，跳过源分支推送；按正常发布的安全规则更新并切换本地发布分支、完成必要合并，再在本地最终 HEAD 创建标签。
- 不校验远端发布分支已包含最终 HEAD，因为本模式不会上传它。返回原分支并明确报告：本地准备已完成、远端未改变、CI 未触发。

## 处理失败与报告结果

- 任一步失败后都停止后续阶段。合并冲突先中止合并；其余情况保留已经成功的提交、分支和标签，不自动 reset、删除或强推。
- 仅在工作区安全且没有进行中的 Git 操作时尽力返回原分支；返回失败时给出当前分支、状态和需要人工处理的原因。
- 分支推送失败前绝不创建标签。标签推送失败时保留本地标签并明确区分本地、远端状态。
- 标签推送成功并校验远端 OID 后即结束。表述为“标签已推送；按已验证配置应触发 CI”，不要表述为“打包成功”；不要轮询 CI，也不要创建托管平台 Release。
- 最终使用中文报告：模式、发布说明路径与提交 OID、源/发布分支及各自推送状态、标签及目标 OID、CI 触发证据与验证状态、已知产物、原分支恢复状态，以及任何保留的本地或远端状态。
